A complete, locally runnable full-stack authentication assignment built with **Flask + SQLite**. It includes password hashing, email-based two-step verification, a protected dashboard, forgot/reset password, automated tests and a generated PDF report.

## 3. Database

The application calls `db.init_db()` at startup, so the database exists before the first request. You can also initialise or inspect it manually:

```bash
cd /home/pc/secure-login-system
.venv/bin/python init_db.py --show
```

Create a clean database (**this deletes all users**):

```bash
.venv/bin/python init_db.py --reset --show
```

`database.db` is stored in the project root. Its `users` table contains the required columns plus operational security fields:

```text
id, username, email, password_hash, otp_code, otp_expiry,
otp_attempts, otp_last_sent, reset_code, reset_expiry,
reset_attempts, reset_last_sent, failed_logins, locked_until,
created_at, last_login_at
```

`otp_code` and `reset_code` store **keyed HMAC-SHA256 digests**, not the plain six-digit codes.

## 4. Email / OTP configuration

The checked-in `.env` is already populated with the supplied SMTP account and the fixed recipient:

```dotenv
MAIL_USERNAME=db1434@gmail.com
OTP_RECIPIENT_OVERRIDE=db1434@gmail.com
```

Every login or password-reset code is therefore sent **only to db1434@gmail.com**, even if a different account email was registered. The code is also always printed in the terminal.

### Demo mode and on-screen code

The ready-to-run `.env` enables:

```dotenv
DEMO_MODE=true
DEMO_SHOW_OTP=true
DEMO_ACCOUNT_USERNAME=demo
DEMO_ACCOUNT_PASSWORD=Demo@1234
```

When SMTP delivery fails, the plaintext code is kept only in the signed browser session so it can be displayed in the green **demo code** banner. The database still stores only the HMAC-SHA256 digest. Once email delivery succeeds, the on-screen fallback is cleared and is not shown.

Set `DEMO_SHOW_OTP=false` (or `DEMO_MODE=false`) to hide the on-screen code; the terminal banner remains available for local testing.

### Important: Gmail requires an App Password

During verification, `smtp.gmail.com:465` was reachable, but Google rejected the supplied credential with:

```text
535 5.7.8 Username and Password not accepted ... BadCredentials
```

Gmail does not allow normal account passwords for SMTP when 2-Step Verification is enabled. To enable live email delivery:

1. Sign in to the Google Account for `db1434@gmail.com`.
2. Enable **2-Step Verification**.
3. Go to **Security → App passwords**.
4. Create an app password for **Mail**.
5. Put the 16-character value in `.env` as `MAIL_PASSWORD=...`.
6. Restart the server.

Until then, the application fails safe: it logs a warning, does not expose SMTP details to the browser, and prints the OTP in the terminal so the full 2FA flow remains testable.

> Do not commit `.env` to source control. It contains secrets.

## 5. Demonstration walkthrough

### Fast path with the demo account

1. Open http://127.0.0.1:5055/login.
2. Sign in with **`demo`** / **`Demo@1234`**.
3. If Gmail delivery is unavailable, the verification page shows the six-digit code in a green **demo code** banner. The same code is printed in the server terminal:

```text
==================================================================
  2FA LOGIN CODE - SECURE LOGIN SYSTEM
------------------------------------------------------------------
  Account : demo (db1434@gmail.com)
  Code    : 482913
  Target  : db1434@gmail.com (authorised owner inbox)
  Expires : 5 minutes
==================================================================
```

4. Enter the code on `/verify-2fa`.
5. The protected `/dashboard` opens. Use **Sign out securely** to end the session.
6. Test recovery: **Forgot password** → enter `db1434@gmail.com` → read the code in the green reset banner or terminal → set a new password.

### Registering a new account

1. Open http://127.0.0.1:5055/register.
2. Create an account with a password that satisfies the policy, for example `StrongPass!23`.
3. Sign in at `/login` with the username or email and that password.
4. Read the code from the green demo banner or the server terminal.
5. Enter the code on `/verify-2fa` to open the protected dashboard.

The OTP page shows a live expiry timer and a resend cooldown. Five wrong OTPs cancel verification; five wrong passwords lock the account for five minutes. The demo login password is nine characters; new passwords and password resets require at least ten characters.

## 9. Security summary

- **Passwords:** Werkzeug scrypt with per-password salt; plaintext is never stored or logged.
- **2FA:** `secrets.randbelow(1_000_000)` OTP, HMAC-hashed at rest, five-minute expiry, single use.
- **Demo fallback:** when SMTP fails, the code is placed in the signed session for on-screen display; the database never stores plaintext.
- **Owner-only delivery:** `OTP_RECIPIENT_OVERRIDE` is applied before every send.
- **Attempts:** five wrong OTPs cancel verification; five wrong passwords trigger a five-minute lock.
- **Sessions:** pending and verified states are separate; the session is cleared and rotated after OTP success.
- **CSRF:** every POST requires a per-session token compared with `hmac.compare_digest`.
- **Responses:** generic login and recovery messages avoid account enumeration.
- **SQL:** all user values are bound parameters.
- **Headers:** CSP, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, restrictive referrer and permissions policies.
- **Database file:** mode `0600` where the OS supports it.

Production hardening (HTTPS, secure cookies, gunicorn, secret manager, server-side session revocation, per-IP rate limiting, audit logging) is discussed in the PDF report.

## 10. Troubleshooting

| Problem | Solution |
| --- | --- |
| Address already in use | Change `PORT` in `.env`; this build defaults to **5055**. |
| No email arrives | Use the green on-screen demo code or check the terminal. Gmail SMTP needs a Google **App Password**; see section 4. |
| `535 BadCredentials` | Replace `MAIL_PASSWORD` with a Gmail App Password and restart. |
| Forgot every account | `python init_db.py --reset --show` (destructive). |
| Server reload not picking up changes | The app runs without the reloader; stop and restart it. |
| Need debug tracebacks | Start with `FLASK_DEBUG=1 .venv/bin/python app.py` only in a local environment. |
